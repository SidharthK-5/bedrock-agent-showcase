# 02 - Postgres DB Agent: One Pattern, Three Deployment Targets

This project is one architectural pattern — **classic Amazon Bedrock Agent → Lambda action group → PostgreSQL** — demonstrated against three different places that Postgres can live. All three subfolders share the same shape: a Bedrock Agent whose action group invokes a Lambda function, and that Lambda function queries a Postgres database and returns structured JSON back to the agent.

| Subfolder | Where Postgres lives | What it demonstrates |
| --- | --- | --- |
| [`docker-local/`](./docker-local) | A local Docker container | Full infrastructure-as-code automation (`setup_infrastructure.py`) standing up Lambda, API Gateway, and IAM from scratch, with the database itself running locally via `docker-compose` and a tunnel exposing it to Lambda |
| [`aws-rds/`](./aws-rds) | Amazon RDS for PostgreSQL | The "normal" production shape — Lambda in (or with network access to) the same VPC as an RDS instance, deployed with a shell script and manually-authored IAM policy documents |
| [`external-azure/`](./external-azure) | An externally-hosted Azure PostgreSQL Flexible Server | Bedrock Agent + Lambda reaching *outside* AWS entirely to a database it doesn't own, including a real SQLAlchemy 1.4 → 2.0 migration story (`external-azure/SQLALCHEMY_MIGRATION.md`) |

Each subfolder is self-contained (its own `pyproject.toml`/`requirements.txt`, its own deployment scripts, its own README) — you don't need the other two to use any one of them. Reading them in the order above roughly tracks increasing deployment complexity: no external network dependency, then a same-cloud managed database, then a genuinely external database on a different cloud provider.

## Shared schema

All three subfolders demonstrate against the same `employees`/`projects` sample schema used in [bedrock-agentcore-showcase](https://github.com/SidharthK-5/bedrock-agentcore-showcase)'s `02-postgres-db-agent`: two tables (`employees`, `projects`), the same seed data, and (in `docker-local/` and `aws-rds/`) the same five operations — list/filter employees, get one by ID, add one, list/filter projects, and department summary statistics. The canonical schema + seed data lives in [`docker-local/init.sql`](./docker-local/init.sql); `aws-rds/schema.sql` and `external-azure/schema.sql` are copies of it for standalone use, since each subfolder is meant to be deployable on its own. `external-azure/` is schema-agnostic by design (it introspects whatever tables already exist on the database you point it at), so its `schema.sql` is optional — only its documentation examples reference `employees`/`projects`.

## Status note (applies to all three subfolders)

All three of these projects were originally built and verified against classic Amazon Bedrock Agents (`agentId`/`agentAliasId`, Lambda action groups, OpenAPI schemas) in a different AWS account/engagement no longer accessible to this repo's maintainer. They're preserved here as reference code — the architecture, deployment scripts, and troubleshooting notes are real and were working at the time — but none of them has been (and none currently *can* be) re-deployed or re-tested in this AWS sandbox, since AWS no longer allows new accounts to create classic Bedrock Agents (only Bedrock AgentCore Runtime is available for new accounts now).

Real hostnames, credentials, and AWS account IDs found in the original projects (an RDS endpoint + password in `bedrock-db-connector`, and an Azure Postgres connection string hardcoded as a Lambda default in `bedrock-agent-ext-source`) have been replaced with placeholders throughout `aws-rds/` and `external-azure/`.

For the same pattern rebuilt on **Bedrock AgentCore Runtime** (Strands Agents) with current, tested/working code, see the companion repo: [bedrock-agentcore-showcase](https://github.com/SidharthK-5/bedrock-agentcore-showcase).

## Judgment calls

- `aws-rds/README.md` was written from scratch by combining the original (empty) `README.md` with the real content of `DEPLOYMENT_GUIDE.md` — the task-relevant deployment guide was simply in the wrong file in the source project.
- `aws-rds/TROUBLESHOOTING.md` is the original `lamda_issue.md` (note the source filename's typo — kept as-is in the commit history but renamed on copy), lightly reformatted into an issue/fix write-up, with the account ID placeholder-ized.
- `aws-rds/` intentionally excludes the vendored `package/` directory (a `pip install -t package/` output containing compiled `psycopg2`/`sqlalchemy` binaries) and the resulting `lambda-deployment.zip` — both are build artifacts, not source, and are regenerated by `deploy.sh`.
- `external-azure/` excludes the same kind of vendored `package/` directory and `lambda_deployment.zip` build artifact.
- `docker-local/`'s two dependency files aren't a duplicate/stale pair despite first appearances: `requirements.txt` (just `psycopg2-binary`) is what `package_lambda.sh` bundles into the Lambda deployment zip, deliberately excluding `boto3` since it already ships with the Lambda Python runtime; `pyproject.toml` carries the full local dev/test dependency set (`boto3` + `psycopg2-binary`, since `test_agent.py`/`setup_infrastructure.py` call Bedrock/IAM/API Gateway from a dev machine where nothing is preinstalled). A `uv.lock` was generated for it (there wasn't one before) so it can be run the same way as the rest of this repo (`uv sync --extra dev`); its four Python files were formatted with `black`. The `.py` files themselves had no structural issues to fix — no duplicated entry points, unlike project 01.
- `aws-rds/`, unlike `docker-local/`, had real duplication bugs, not just doc bloat: its `README.md` repeated an entire "Test Your Agent" + "Grant Lambda Permission" pair of steps verbatim (mislabeled as Step 8/9 a second time, after the same content already appeared as Step 7 and Step 9 earlier) — the shorter, later duplicate was deleted. Its plain `requirements.txt` was a stale, incorrect duplicate of `lambda-requirements.txt` (missing `sqlalchemy`, which `lambda_function.py` actually imports, and referenced by nothing) — deleted. `main.py` was an unused, unreferenced placeholder (`print("Hello from bedrock-db-connector!")`) — deleted, same call as project 01's `STATUS.md`. Two more places in `README.md` re-typed an incomplete version of `deploy.sh`'s package-build command (missing the `--platform`/`--python-version` flags `TROUBLESHOOTING.md` says are required) — both now just point to `deploy.sh` and `TROUBLESHOOTING.md` instead of repeating it. `lambda_function.py` was formatted with `black`.
- Unified all three subfolders onto the same `employees`/`projects` sample schema (originally only `docker-local/` used it; `aws-rds/` had its own unrelated `workspaces`/`documents` + RFP-document sample, and `external-azure/` used a generic unrelated `users`/`orders` placeholder in its examples). `aws-rds/lambda_function.py`'s `get_workspace_by_id`/`get_rfp_documents_by_workspace` were replaced with `get_employees`/`get_employee_by_id`/`get_projects`/`get_department_summary`/`add_employee` (SQLAlchemy `text()`-based, same route shape as `docker-local/api-schema.yaml`); `bedrock-agent-schema.json`, `test-event.json`, and every example/instruction-text reference in `README.md` were updated to match, and a new `schema.sql` (identical SQL to `docker-local/init.sql`) was added since `aws-rds/` never had a schema-creation step at all — it previously assumed a pre-existing production database. `external-azure/` is intentionally schema-agnostic (dynamic introspection, not hardcoded queries), so its Python code needed no changes — only its example queries/instructions across `README.md`, `SETUP_GUIDE.md`, `bedrock_agent_schema.json`, `MIGRATION_QUICK_REF.md`, and `SQLALCHEMY_MIGRATION.md` were updated from generic `users`/`orders` table names to `employees`/`projects`, and an optional `schema.sql` was added for anyone trying it against a scratch database.
- `external-azure/` had its own real bugs beyond the schema sample, on top of being schema-agnostic code: `pyproject.toml`'s `[build-system]` section made `uv sync` fail outright (`hatchling` couldn't find a package to ship — same root cause as project 01's bug) — removed, since this project is Lambda-deployed source, not an installable package; a `uv.lock` was generated for it for the first time. `requirements.txt` still listed `psycopg2-binary==2.9.9` and a redundant bare `psycopg>=3.2.3` line even though `SQLALCHEMY_MIGRATION.md` explicitly documents `psycopg2-binary` as "Removed" during this project's own psycopg2→psycopg3 migration — both deleted, `pyproject.toml` updated to match (`psycopg[binary]` instead of `psycopg2-binary`). `build_lambda.sh` had a copy-paste bug: it copied the three source files and zipped them *twice*, once into a dead, never-referenced `lambda-deployment.zip` (hyphen) and again into the actually-used `lambda_deployment.zip` (underscore) — the first pass was deleted. Separately, `README.md`, `.env.example`, and two spots in `SETUP_GUIDE.md` all showed the connection URI as plain `postgresql://`, but the code (`main.py`'s own default) and `MIGRATION_QUICK_REF.md` require the `postgresql+psycopg://` driver spec for SQLAlchemy to use psycopg3 instead of defaulting to the no-longer-installed psycopg2 — all four fixed to match. `SQLALCHEMY_MIGRATION.md` separately and incorrectly claimed "no changes needed to connection strings," directly contradicting its own sibling doc and the actual code — fixed to point at `MIGRATION_QUICK_REF.md`'s correct explanation instead of repeating (and getting wrong) the same fact twice. `main.py`/`db_connector.py`/`query_router.py` were formatted with `black`.
- Consolidated `.gitignore` handling: `docker-local/.gitignore` duplicated patterns (`__pycache__/`, `*.py[oc]`, `.venv`) already in the repo root `.gitignore`, so it was deleted — `build/`, `dist/`, `wheels/` (the only patterns it had that the root didn't) were folded into the root `.gitignore` instead. Neither `aws-rds/` nor `external-azure/` ever had their own `.gitignore`; none of the three subprojects need one now that the root file is the single common source.
